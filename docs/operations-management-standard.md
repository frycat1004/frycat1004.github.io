## 제1장 총칙

### 1.1 목적

이 기준은 회사가 운영하는 정보시스템, 서비스·플랫폼, 대외 유지관리 사업, 프로젝트와 조직 운영에 대해 **누가(역할), 무엇을(활동), 어느 수준으로(목표), 어떤 절차로(프로세스), 어떻게 증명하는가(기록·지표)**를 통일된 언어로 정하는 데 목적이 있다.

운영관리 기준이 없으면 같은 장애를 팀마다 다른 방식으로 처리하고, 같은 "긴급"이라는 말이 사람마다 다른 뜻으로 쓰인다. 이 문서는 그 **공통 자(ruler)** 역할을 한다.

### 1.2 적용 범위

| 영역 | 포함 대상 | 제외 대상 |
|---|---|---|
| ① IT 서비스·시스템 운영 | 회사가 소유·운영하는 서버, 클라우드, 네트워크, 애플리케이션, 데이터베이스, 모니터링, 백업, 보안 운영 | 개인 업무용 단말의 사용 규칙 (정보보호 규정에서 별도 관리) |
| ② SW 유지관리·운영 사업 | 고객사와 계약한 유지관리·운영 용역, SLA 기반 서비스, 하자보수 | 신규 구축(SI) 프로젝트의 개발 단계 (제6장 프로젝트 기준 적용) |
| ③ 서비스·플랫폼 운영 | 고객 지원(CS/VOC), 콘텐츠·정책 운영, 이용자 관리, 공지·약관, 정산·결제 운영, 서비스 지표 관리 | 마케팅 캠페인 집행 (마케팅 규정) |
| ④ 프로젝트·조직 운영 | PMO, 일정·리소스·리스크 관리, 회의·보고 체계, 의사결정 권한, 포트폴리오 관리 | 인사 평가·보상 (인사 규정) |
| ⑤ 신규 시스템 운영 전환 | 사내에서 개발·도입한 시스템을 운영 조직으로 인수하는 절차, 운영 준비도 점검, 하이퍼케어 | — |

### 1.3 문서의 위계

운영 관련 문서는 아래 4단계로 관리한다. 비유하면 **규정은 헌법, 기준은 법률, 절차는 시행령, 가이드는 해설서**에 해당한다. 상위 문서와 충돌하는 하위 문서는 효력이 없다.

| 단계 | 문서 종류 | 예시 | 승인 권한 |
|---|---|---|---|
| 1 | 규정 (Policy) | 정보보호 규정, 내부통제 규정 | 대표이사 |
| 2 | **기준 (Standard) — 이 문서** | 운영관리 기준, 보안 기준 | `[결정 필요]` CTO/COO |
| 3 | 절차 (Procedure / SOP) | 장애 대응 절차, 변경 승인 절차, 배포 절차, 백업·복구 절차 | 운영총괄 |
| 4 | 가이드·런북 (Guide / Runbook) | 시스템별 운영 매뉴얼, 체크리스트, 템플릿 | 각 서비스 오너 |

### 1.4 용어 정의

| 용어 | 정의 |
|---|---|
| 서비스 (Service) | 이용자에게 가치를 제공하는 기능의 묶음. 하나 이상의 시스템으로 구성된다. |
| 시스템 (System) | 서비스를 구성하는 기술적 단위 (애플리케이션, DB, 인프라). |
| 서비스 오너 (Service Owner) | 서비스의 비즈니스 결과와 운영 수준에 최종 책임을 지는 사람 (PO/기획 책임자). |
| 운영 관리자 (Operations Manager) | 운영 프로세스(장애·변경·배포·모니터링)의 실행과 보고를 책임지는 사람. |
| 사건 / 장애 (Incident) | 서비스의 계획되지 않은 중단 또는 품질 저하. ITIL 4의 incident 정의를 따른다. |
| 문제 (Problem) | 하나 이상의 장애를 일으키는 (또는 일으킬 수 있는) 근본 원인. |
| 변경 (Change) | 서비스에 직·간접 영향을 줄 수 있는 모든 추가·수정·제거. |
| SLI / SLO / SLA | SLI는 서비스 수준을 수치로 측정한 지표, SLO는 그 지표의 내부 목표값, SLA는 고객과 계약으로 약속한 수준과 미달 시 결과. (Google SRE Book 4장 정의 준용) |
| 에러 버짓 (Error Budget) | 100% − SLO. 허용된 실패 한도. |
| RTO / RPO | RTO는 장애 후 서비스를 복구해야 하는 목표 시간, RPO는 복구 시 허용되는 데이터 손실 범위(시점). (ISO 22300 용어 준용) |
| 하이퍼케어 (Hypercare) | 신규 시스템 오픈 직후, 개발팀과 운영팀이 공동으로 집중 지원하는 기간. |
| 운영 준비도 점검 (ORR) | Operational Readiness Review. 운영 인수 전 운영 가능 상태를 체크리스트로 확인하는 심사. |

### 1.5 준거 기준 (참조 프레임워크 선정 근거)

사용자의 요청에 따라 적절한 참조 기준을 아래와 같이 선정했다. 선정 원칙은 **① 국제적으로 통용되고 ② 국내 법령·공공 가이드와 호환되며 ③ 과도한 문서 부담 없이 중소·중견 조직에 적용 가능한 것**이다.

| 영역 | 1차 준거 (골격) | 2차 준거 (보완) | 선정 이유 |
|---|---|---|---|
| IT 서비스 운영 공통 | **ITIL 4** 관리 프랙티스 (34개: 일반 14, 서비스 17, 기술 3) | **ISO/IEC 20000-1:2018** (서비스관리시스템 요구사항, Annex SL 구조) | ITIL은 용어·프로세스의 사실상 표준이고, ISO 20000-1은 인증 가능한 요구사항이므로 향후 인증 시 재작업이 없음 |
| 신뢰성·지표 | **Google SRE Book / Workbook** (SLI·SLO·에러 버짓) | **DORA 4대 지표** (State of DevOps Report) | 가용성 목표와 배포 성과를 수치로 관리하는 가장 널리 검증된 방법 |
| 정보보호·개인정보 | **ISMS-P 인증기준** (101개: 관리체계 16, 보호대책 64, 개인정보 처리단계 21) | **ISO/IEC 27001:2022** Annex A (93개 통제, 4개 영역), **개인정보보호법 및 안전성 확보조치 기준**, **정보통신망법** | 국내 법적 의무와 직접 연결되는 기준은 ISMS-P이며, 글로벌 고객 대응에는 ISO 27001 매핑이 필요 |
| 보안사고 대응 | **NIST SP 800-61 Rev.3** (2025.4, CSF 2.0 Community Profile) | — | 2012년판 이후 첫 전면 개정으로 최신 사고대응 수명주기를 제시 |
| 업무 연속성 | **ISO 22301:2019** (BCMS) / ISO 22300 용어 | — | RTO·RPO·BIA의 표준 정의 제공 |
| 대외 유지관리 사업 | **소프트웨어 진흥법** (하자담보책임), **SW사업 대가산정 가이드 2025년판 (KOSA)** | 행정안전부 **공공 SLA 표준** (2026년 의무화 추진), 전자정부 성과관리 지침 | 공공·대기업 고객의 계약 기준과 직접 연결 |
| 프로젝트·조직 운영 | **PMBOK Guide 7판** (12원칙, 8성과영역) | PMBOK 8판 (6원칙, 7성과영역, 7판은 2026.7.8까지 제공) | 사내 PMO 체계의 공통 언어. 8판 전환은 부록 I 참고 |

> **주의**: ITIL은 2026년 1월 "ITIL 5(Version 5)"가 발표되어 프랙티스 분류가 2개 그룹으로 바뀌었다는 자료가 있다(단일 출처). 이 문서는 널리 보급된 ITIL 4 분류를 사용하되, 공식 PeopleCert 자료로 재확인 후 다음 개정에 반영한다.

**[준거]** ITIL 4 프랙티스 구성, ISO/IEC 20000-1:2018 구조, ISMS-P 101개 항목 구성, ISO/IEC 27001:2022 93개 통제, NIST SP 800-61r3 발행(2025.4.3), ISO 22300 RTO/RPO 정의 — 부록 H 참조.

## 제2장 운영관리 거버넌스 (공통)

### 2.1 운영 조직과 역할

운영은 "한 사람이 다 하는 일"이 아니라 **역할의 분리**가 핵심이다. 작은 조직에서는 한 사람이 여러 역할을 겸할 수 있지만, 역할 자체는 분리해 정의해야 **겸직 시 어떤 통제가 약해지는지** 알 수 있다 (예: 변경 요청자와 승인자가 같은 사람이면 승인 통제가 무력화된다).

| 역할 | 핵심 책임 | 비유 |
|---|---|---|
| 운영총괄 (COO/CTO급) `[결정 필요]` | 기준 승인, 자원 배분, P1 장애 최종 의사결정, 대외 공표 승인 | 병원장 |
| 서비스 오너 (PO) | 서비스별 SLO 확정, 우선순위 결정, 변경 승인(비즈니스 관점), 성과 책임 | 진료과장 |
| 운영 관리자 (Ops Manager) | 운영 프로세스 실행·보고, 장애 지휘(Incident Commander), 변경자문위원회(CAB) 운영 | 수간호사/병동장 |
| 시스템 운영 담당 (SRE / 인프라 / DBA) | 모니터링, 배포, 백업·복구, 용량 관리, 런북 유지 | 당직 의료진 |
| 개발 담당 | 코드 변경, 핫픽스, 근본원인 분석 지원, 하이퍼케어 참여 | 전문 진료팀 |
| 정보보호·개인정보 담당 (CISO/CPO) | 접근권한 심사, 보안사고 대응, 법정 신고, 취약점 관리 | 감염관리실 |
| 고객지원 담당 (CS) | 1차 접점, VOC 분류, 이용자 공지, 장애 시 고객 커뮤니케이션 | 원무과 |
| PMO | 프로젝트 포트폴리오, 일정·리소스·리스크 통합 관리, 보고 표준 | 기획조정실 |
| 사업관리 담당 | 계약·SLA·대가·검수·보고서 제출, 과업 변경 협의 | 원무·보험심사 |

역할별 RACI(책임 분담표)는 **부록 D**에 둔다.

### 2.2 회의체와 보고 체계

| 회의체 | 주기 | 참석 | 주요 안건 | 산출물 |
|---|---|---|---|---|
| 일일 운영 스탠드업 | 매 영업일 (15분) | 운영 관리자, 시스템 운영, 온콜 담당 | 전일 장애·알람, 금일 배포·변경, 리스크 | 일일 운영 로그 |
| 변경자문위원회 (CAB) | 주 1회 + 긴급 소집 | 운영 관리자(의장), 서비스 오너, 개발 리드, 보안 담당 | 정상 변경 승인, 배포 일정 조정, 변경 충돌 검토 | 변경 승인 기록 |
| 월간 운영 리뷰 | 월 1회 | 운영총괄, 서비스 오너 전원, PMO, 사업관리 | SLO 달성률, 장애 통계, 에러 버짓 소진, 용량 전망, 보안 점검 결과, 고객 SLA 보고 | 월간 운영 보고서 |
| 분기 운영위원회 | 분기 1회 | 경영진, 운영총괄, 각 책임자 | 투자·인력 결정, 서비스 등급 재조정, 기준 개정, 폐기·통합 판단 | 운영위원회 의결서 |
| 장애 사후검토 (Post-Incident Review) | P1·P2 장애 종료 후 5영업일 이내 | 장애 관련자 전원 | 타임라인, 근본 원인, 재발 방지 과제 | 사후검토 보고서 (비난 없는 포스트모템) |

보고 원칙:
1. **보고서의 숫자는 시스템에서 자동 집계**한 값을 우선한다. 수작업 집계는 출처와 집계 방식을 명시한다.
2. 보고서에는 **목표 대비 실적**과 **전월 대비 추세**를 함께 적는다. 실적만 있으면 판단이 불가능하다.
3. 미달 항목은 반드시 **원인과 조치 계획**을 같이 쓴다.

### 2.3 의사결정과 결재 권한

| 결정 사항 | 결정 권한 | 협의 |
|---|---|---|
| 운영관리 기준 제·개정 | `[결정 필요]` 대표이사 또는 CTO/COO | 운영위원회 |
| 서비스 등급(Tier) 부여·변경 | 운영위원회 | 서비스 오너, 운영 관리자 |
| SLO 목표값 확정 | 서비스 오너 | 운영 관리자 (달성 가능성 검토) |
| 정상 변경 승인 | CAB | — |
| 긴급 변경 승인 | 운영 관리자 + 서비스 오너 (사후 CAB 보고) | 보안 담당 (보안 관련 시) |
| P1 장애 시 서비스 중단·롤백·대외 공지 | 운영총괄 (부재 시 운영 관리자 대행) | 서비스 오너, CS, 법무 |
| 개인정보 유출·침해사고 법정 신고 | CPO/CISO (대표이사 보고 병행) | 법무 |
| 대외 SLA 조건 합의 | 사업관리 담당 + 운영총괄 | 운영 관리자 (이행 가능성 검토 필수) |
| 시스템 폐기·통합 | 운영위원회 | 서비스 오너, 보안 담당 (데이터 파기) |

### 2.4 위험 관리

- 운영 리스크 등록부(Risk Register)를 서비스별로 유지하고 **월간 운영 리뷰에서 갱신**한다.
- 리스크는 **발생 가능성(1~5) × 영향도(1~5)**로 점수화하고, 15점 이상은 운영위원회에 보고한다 `[결정 필요]`.
- 대응 유형은 회피·완화·전가(보험·계약)·수용 중 하나로 명시하고 담당자와 기한을 둔다.
- ISO/IEC 20000-1과 ISO/IEC 27001은 모두 **리스크 기반 접근**을 요구하므로, 보안 리스크와 운영 리스크 등록부는 **같은 척도**를 쓴다.

### 2.5 기록과 증적

운영 활동은 "했다"가 아니라 **"했음을 보여줄 수 있다"**가 기준이다. 인증 심사와 고객 감사는 증적으로만 판단한다.

| 기록 | 최소 보존 기간 | 근거 |
|---|---|---|
| 장애 기록, 변경 기록, 배포 기록 | 3년 `[결정 필요]` | ISO/IEC 20000-1 문서화된 정보 요구, 내부 감사 주기 |
| 개인정보처리시스템 접속기록 | **1년 이상** (일정 요건 시 **2년 이상**) | 개인정보의 안전성 확보조치 기준 제8조 |
| 접근권한 부여·변경·말소 내역 | **3년 이상** | 개인정보의 안전성 확보조치 기준 제5조 제3항 |
| 백업 매체 및 복구 테스트 결과 | 복구 테스트 결과는 3년 | ISO 22301 연습·시험 기록 요구 |
| 고객 SLA 보고서 | 계약 종료 후 5년 `[결정 필요]` | 계약 분쟁 대비 (상법상 상업장부 보존 10년과 별개로 사내 결정) |

**[준거]** ISO/IEC 20000-1:2018 (리더십·운영·성과평가 조항), 개인정보의 안전성 확보조치 기준 제5조·제8조, ISO 22301.

## 제3장 IT 서비스·시스템 운영 기준

### 3.1 서비스 카탈로그와 구성관리

1. 회사가 운영하는 모든 서비스는 **서비스 카탈로그**에 등록한다. 카탈로그 미등록 시스템은 운영 대상이 아니며, 발견 즉시 등록 또는 폐기한다 (섀도 IT 통제).
2. 카탈로그 필수 항목: 서비스명, 서비스 오너, 운영 관리자, 서비스 등급(Tier), SLO, 구성 시스템, 의존 서비스(외부 API·SaaS 포함), 데이터 분류(개인정보 포함 여부), 지원 시간, 런북 위치.
3. 구성 항목(CI)은 **구성관리 데이터베이스(CMDB)** 또는 그에 준하는 IaC(Infrastructure as Code) 저장소로 관리하고, **변경 기록과 연결**한다.
4. 카탈로그와 CMDB는 **분기 1회 정합성 점검**을 한다.

### 3.2 서비스 등급 (Tier) 분류

모든 서비스는 비즈니스 영향도에 따라 3등급으로 나눈다. 등급은 **투입 자원과 목표 수준을 결정하는 기준**이므로, 모든 서비스를 1등급으로 두면 기준의 의미가 없어진다.

| 등급 | 정의 | 가용성 SLO (예시) | 월 허용 중단 (30일 기준) | RTO / RPO (예시) | 지원 시간 | 모니터링 |
|---|---|---|---|---|---|---|
| **Tier 1 (핵심)** | 매출·대외 서비스에 직결, 중단 시 즉시 손실 또는 법적 문제 | 99.9% `[결정 필요]` | 약 43분 | RTO 4시간 / RPO 1시간 | 24×7 온콜 | 실시간 알림, 외부 가용성 체크 |
| **Tier 2 (중요)** | 내부 핵심 업무, 중단 시 업무 지연 | 99.5% `[결정 필요]` | 약 3.6시간 | RTO 8시간 / RPO 4시간 | 평일 09–18 + 온콜 | 실시간 알림 |
| **Tier 3 (일반)** | 내부 지원·참고용, 우회 수단 존재 | 99.0% `[결정 필요]` | 약 7.2시간 | RTO 24시간 / RPO 24시간 | 업무 시간 | 일 단위 점검 |

- 가용성 99.9%는 "월 43분만 멈출 수 있다"는 뜻이다. 비유하면 **에러 버짓은 월간 가계 예산**이다. 장애로 예산을 다 쓰면 그 달에는 위험한 배포(지출)를 줄여야 한다 (3.6 참조).
- 등급은 서비스 오너가 제안하고 **운영위원회가 확정**한다. 연 1회 재검토한다.

### 3.3 모니터링과 관측성 (Observability)

1. Tier 1·2 서비스는 다음 4가지 **골든 시그널**을 SLI로 수집한다: **지연시간(Latency), 트래픽(Traffic), 오류율(Errors), 포화도(Saturation)** (Google SRE Book 6장 "Monitoring Distributed Systems" 준용).
2. 알림(Alert)은 **"사람이 지금 행동해야 하는 것"**만 보낸다. 조치가 필요 없는 알림은 대시보드로 내린다. 알림 피로는 실제 장애를 놓치게 만드는 가장 큰 원인이다.
3. 모든 알림에는 **런북 링크**가 있어야 한다. 런북 없는 알림은 생성 금지.
4. 로그는 중앙 수집하고, 개인정보가 포함될 수 있는 로그는 **마스킹 또는 접근 통제**를 적용한다 (ISMS-P 2.9.4 로그 및 접속기록 관리, 2.9.5 로그 및 접속기록 점검 항목 대응).
5. 외부 의존 서비스(클라우드, 결제 PG, 문자 발송, 외부 API)는 **자체 가용성 모니터링**을 둔다. 상대방 상태 페이지만 믿지 않는다.

### 3.4 장애 관리 (Incident Management)

#### 3.4.1 장애 등급

ITIL 4는 우선순위를 **영향도(Impact) × 긴급도(Urgency)**로 정한다. 이를 단순화해 4등급으로 운영한다.

| 등급 | 정의 (예시) | 최초 대응 (인지→착수) | 상황 공유 주기 | 목표 복구 시간 | 지휘 |
|---|---|---|---|---|---|
| **P1 (치명)** | Tier 1 전면 중단, 결제·로그인 불가, 데이터 유출·훼손 의심, 다수 고객 영향 | 15분 `[결정 필요]` | 30분마다 | 4시간 | Incident Commander 지정, 운영총괄 즉시 보고 |
| **P2 (높음)** | 주요 기능 장애, Tier 1 성능 심각 저하, Tier 2 전면 중단 | 30분 | 1시간마다 | 8시간 | 운영 관리자 |
| **P3 (보통)** | 일부 기능 장애, 우회 수단 존재, 소수 이용자 영향 | 2시간 (업무시간 기준) | 일 1회 | 3영업일 | 담당자 |
| **P4 (낮음)** | 경미한 오류, 문의성 이슈, 미관 문제 | 1영업일 | — | 10영업일 | 담당자 |

#### 3.4.2 대응 절차 (수명주기)

NIST SP 800-61 Rev.3와 ITIL 4의 흐름을 통합해 아래 6단계로 운영한다.

1. **감지·접수** — 모니터링 알림, CS 접수, 내부 신고. 모든 장애는 **티켓 번호**를 부여한다.
2. **분류·등급 부여** — 15분 이내 임시 등급 부여. 등급은 상황 변화에 따라 상향·하향 가능하며, 변경 사유를 기록한다.
3. **초동 대응·공유** — P1·P2는 전용 커뮤니케이션 채널(워룸)을 열고 Incident Commander가 역할(조치/기록/소통)을 분배한다. **조치하는 사람과 소통하는 사람은 분리**한다.
4. **복구** — 원칙은 **"원인 규명보다 서비스 복구 우선"**. 롤백·페일오버·재시작 등 알려진 복구 수단을 먼저 쓴다. 근본 원인 분석은 복구 후 문제관리로 넘긴다.
5. **종료·공지** — 복구 확인(모니터링 지표 정상 + 재현 테스트) 후 종료. 고객 영향이 있었으면 CS와 협의해 공지문을 발송한다.
6. **사후검토** — P1·P2는 5영업일 이내 **비난 없는 포스트모템(Blameless Postmortem)**을 작성한다. 필수 항목: 타임라인, 영향 범위(이용자 수, 시간, 매출), 근본 원인, 잘된 점, 운이 좋았던 점, 재발 방지 과제(담당·기한).

#### 3.4.3 에스컬레이션

| 조건 | 에스컬레이션 대상 |
|---|---|
| P1 발생 즉시 | 운영총괄, 서비스 오너, CS 리드, (개인정보 관련 시) CPO |
| P1이 목표 복구 시간의 50%를 넘김 | 대표이사 보고, 외부 전문업체·벤더 지원 요청 결정 |
| P2가 목표 복구 시간을 넘김 | 운영총괄 |
| 동일 원인 장애가 30일 내 2회 이상 | 문제관리 등록 의무, 월간 운영 리뷰 안건 |

#### 3.4.4 보안·개인정보 사고의 법정 신고 (장애 대응과 병행)

보안사고는 일반 장애와 **별도의 법정 시계**가 돌아간다. 복구에만 집중하다 신고 기한을 놓치면 과태료와 신뢰 손실이 발생한다.

| 사고 유형 | 의무 | 기한 | 신고처 | 근거 |
|---|---|---|---|---|
| 개인정보 유출 (1천명 이상, 민감·고유식별정보, 외부 불법 접근에 의한 유출) | 신고 | **알게 된 때부터 72시간 이내** | 개인정보보호위원회 / 한국인터넷진흥원(KISA) | 개인정보보호법 제34조, 시행령 제40조 (2023.9.15 시행) |
| 개인정보 유출 (모든 경우) | 정보주체 통지 | **72시간 이내** (정당한 사유 없는 한) | 정보주체 | 개인정보보호법 제34조 |
| 침해사고 (해킹, 악성코드, DDoS 등) — 정보통신서비스 제공자 | 신고 | **인지한 때부터 24시간 이내** (최초 신고 후 보완 신고) | 과학기술정보통신부 / KISA | 정보통신망법 제48조의3 (2024.8 개정, 2026.3 재개정) |

> 2026년 3월 국회를 통과한 정보통신망법 개정안은 신고 지연 시 과태료, 신고 후 14일 이내 이용자 피해구제 조치 제출(시행령안) 등을 담고 있으며 공포 후 6개월 뒤 시행된다. 정확한 시행일은 부록 I에 따라 확인한다.

사고 대응 절차에는 **"신고 여부 판단"을 P1 체크리스트의 첫 항목**으로 둔다. 판단 권한은 CPO/CISO이며, 판단 근거를 기록한다.

### 3.5 문제 관리 (Problem Management)

1. 다음 경우는 문제(Problem)로 등록한다: P1·P2 장애 전부, 30일 내 동일 원인 장애 2회 이상, 사후검토에서 근본 원인 미확정인 건.
2. 근본 원인 분석은 5 Whys, 피시본, 장애 트리 중 상황에 맞는 기법을 쓰되, **"사람 실수"를 근본 원인으로 끝내지 않는다**. 실수를 가능하게 한 시스템·절차의 결함까지 내려간다.
3. 근본 원인을 즉시 제거할 수 없으면 **알려진 오류(Known Error)**와 **우회책(Workaround)**을 지식베이스에 등록해 1차 대응 시간을 줄인다.
4. 재발 방지 과제는 **백로그에 등록하고 완료 여부를 월간 운영 리뷰에서 추적**한다. 포스트모템을 쓰고 과제가 사라지는 것이 가장 흔한 실패다.

### 3.6 변경 관리 (Change Enablement)

#### 3.6.1 변경 유형

ITIL 4의 변경 유형 분류를 따른다.

| 유형 | 정의 | 승인 | 예시 |
|---|---|---|---|
| **표준 변경 (Standard)** | 위험이 낮고 절차가 정해져 사전 승인된 반복 변경 | 사전 승인 (티켓 기록만) | 인증서 갱신, 디스크 증설, 승인된 파이프라인을 통한 정기 배포 |
| **정상 변경 (Normal)** | 평가·승인이 필요한 일반 변경 | CAB (주 1회) | 스키마 변경, 신규 기능 배포, 인프라 구성 변경, 외부 연동 변경 |
| **긴급 변경 (Emergency)** | 장애 복구나 보안 패치처럼 지연할 수 없는 변경 | 운영 관리자 + 서비스 오너 구두·채팅 승인, **24시간 내 사후 기록·CAB 보고** | 핫픽스, 긴급 보안 패치, 장애 롤백 |

#### 3.6.2 변경 요청 필수 항목

변경 사유, 영향 범위(서비스·이용자·데이터), 위험 평가, **롤백 계획**, 테스트 결과, 작업 일정(변경 금지 시간대 확인), 작업자·승인자, 사후 검증 방법.

**롤백 계획이 없는 변경은 승인하지 않는다.**

#### 3.6.3 변경 금지 시간대 (Change Freeze)

- Tier 1 서비스의 정상 변경은 **트래픽 피크 시간대, 금요일 오후, 공휴일 전일, 월말 정산일**에 금지한다 `[결정 필요]`.
- 대규모 프로모션·결산 등 비즈니스 이벤트 기간은 서비스 오너가 금지 기간을 사전 등록한다.

#### 3.6.4 에러 버짓 정책

- 에러 버짓이 **소진(해당 월 SLO 미달)**되면 해당 서비스의 정상 변경은 신뢰성 개선 변경을 제외하고 **다음 측정 주기까지 동결**한다. 서비스 오너와 운영 관리자가 합의하면 예외를 둘 수 있으며 예외는 기록한다.
- 이 규칙의 목적은 **"속도와 안정성 사이의 다툼을 사전에 정한 숫자로 해결"**하는 것이다 (Google SRE Book 3장 "Embracing Risk").

### 3.7 배포·릴리스 관리

1. 배포는 **승인된 자동화 파이프라인**으로만 수행한다. 운영 서버 직접 접속 후 수동 배포는 긴급 변경에서만 허용하고 기록한다.
2. Tier 1 서비스의 배포는 **점진 배포(카나리/블루그린)**를 원칙으로 하고, 배포 후 **30분 이상 핵심 SLI를 관찰**한 뒤 완료 처리한다 `[결정 필요]`.
3. 배포 성과는 **DORA 4대 지표**로 월간 측정한다.

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| 배포 빈도 (Deployment Frequency) | 운영 환경 배포 횟수 | 파이프라인 로그 |
| 변경 리드타임 (Lead Time for Changes) | 커밋 → 운영 반영까지 시간 | VCS + 파이프라인 |
| 변경 실패율 (Change Failure Rate) | 배포 후 장애·롤백·핫픽스를 유발한 배포 비율 | 배포 기록과 장애 기록 연결 |
| 복구 시간 (Failed Deployment Recovery Time) | 실패한 배포에서 복구까지 시간 | 장애 기록 |

> DORA 2024 보고서는 네 번째 지표를 "failed deployment recovery time"으로 명명했다. 과거 자료의 MTTR과 같은 취지다. 지표를 **팀 간 경쟁 수단으로 쓰지 않는다** (지표를 목표로 삼으면 왜곡된다는 비판이 있다).

### 3.8 용량·성능 관리

1. Tier 1·2 서비스는 CPU, 메모리, 스토리지, DB 커넥션, 큐 길이, 외부 API 할당량의 **사용률 추세를 월간 보고**한다.
2. 임계치: 사용률 70% 도달 시 증설 계획 수립, 85% 도달 시 증설 실행 `[결정 필요]`.
3. 대규모 이벤트(프로모션, 신학기, 결산) 전에는 **부하 테스트 또는 사전 증설**을 하고 결과를 기록한다.
4. 클라우드 비용은 용량 관리의 일부다. 월간 비용을 서비스별로 배분(태깅)하고 **전월 대비 20% 이상 증감은 원인을 보고**한다 `[결정 필요]`.

### 3.9 가용성·연속성 관리 (백업·DR)

| 항목 | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|
| 백업 주기 (예시) | 일 1회 전체 + 시간 단위 증분/트랜잭션 로그 (RPO 1h) | 일 1회 전체 (RPO 4h는 로그 백업으로 보완) | 일 1회 |
| 백업 보존 | 일 30일, 월 12개월 `[결정 필요]` | 일 14일, 월 6개월 | 일 7일 |
| 오프사이트/타 리전 보관 | 필수 | 필수 | 권장 |
| **복구 테스트** | **분기 1회** 실제 복원 | 반기 1회 | 연 1회 |
| DR 전환 훈련 | 연 1회 (모의 포함) | 연 1회 (탁상 훈련) | — |

- **복원해 보지 않은 백업은 백업이 아니다.** 복구 테스트 결과(소요 시간, 데이터 정합성)를 기록하고 RTO·RPO 달성 여부를 판정한다.
- 백업 데이터는 운영 데이터와 **동일 수준의 접근 통제·암호화**를 적용한다. 백업에서 개인정보가 유출되는 사고가 실제로 많다.
- 업무영향분석(BIA)을 연 1회 갱신해 RTO·RPO가 비즈니스 요구와 맞는지 확인한다 (ISO 22301).

### 3.10 정보보호·개인정보 운영 통제

이 절은 정보보호 규정의 하위가 아니라, **운영 조직이 매일 지켜야 하는 최소 통제**를 모은 것이다. 세부는 정보보호 규정과 ISMS-P 통제 매핑표(부록, 추후 작성)를 따른다.

1. **접근권한**: 최소 권한 원칙. 운영 환경 접근은 개인 계정 + MFA, 공용 계정 금지. 권한 부여·변경·말소는 승인 기록을 남기고 **3년 이상 보존**. 퇴직·전배 시 **당일 회수**. 권한 적정성은 **분기 1회 검토**.
2. **접속기록**: 개인정보처리시스템 접속기록은 **1년 이상 보존**(일정 요건 시 2년 이상), 위·변조 방지 조치, **점검 주기·방법·사후조치 절차를 내부관리계획에 명시**해 이행. (종전 고시의 "월 1회 이상 점검"은 개정으로 내부관리계획 위임 방식으로 바뀌었으나, 이 기준에서는 **월 1회 점검을 사내 기준으로 유지**한다.)
3. **취약점·패치**: 치명(Critical) 취약점은 공개 후 **14일 이내**, 높음(High)은 30일 이내 패치 또는 완화 조치 `[결정 필요]`. 연 1회 이상 모의해킹 또는 취약점 진단.
4. **개인정보 처리**: 개인정보 처리 시스템 목록과 처리 흐름도를 유지하고, 신규 시스템은 운영 전환 전 **개인정보 영향 검토**를 거친다 (ISMS-P 3장 개인정보 처리단계별 요구사항 21개 항목 대응).
5. **외부 위탁·공급업체**: 클라우드·SaaS·외주 운영사는 계약에 보안 요구사항과 사고 통지 의무를 넣고, 연 1회 점검한다 (ITIL 4 supplier management, ISO 27001 A.5.19~5.23).
6. **암호화**: 개인정보·인증정보는 저장·전송 시 암호화. 키 관리 책임자를 지정한다.

### 3.11 지식 관리와 문서화

1. 서비스별 **런북**은 다음을 반드시 포함한다: 아키텍처 개요, 접속 방법, 시작/중지/재시작 절차, 주요 알림별 대응 절차, 백업·복구 절차, 담당자·에스컬레이션 연락망, 외부 벤더 연락처.
2. 런북은 **장애 대응에서 실제 사용된 뒤 갱신**한다. 포스트모템의 재발 방지 과제에 "런북 갱신"을 기본 포함한다.
3. 문서는 버전 관리 저장소에 두고, 분기 1회 **"신입 운영자가 런북만 보고 복구할 수 있는가"**를 기준으로 검토한다.

**[준거]** ITIL 4 (incident, problem, change enablement, deployment, service level, monitoring and event, supplier management), Google SRE Book 3·4·6장, DORA State of DevOps 2021·2024, NIST SP 800-61r3, 개인정보보호법 제34조·시행령 제40조, 개인정보의 안전성 확보조치 기준 제5조·제8조, 정보통신망법 제48조의3, ISMS-P 2.9 시스템 및 서비스 운영관리, ISO/IEC 27001:2022 Annex A, ISO 22301.

## 제4장 서비스·플랫폼 운영 기준 (비즈니스 운영)

시스템이 정상이어도 서비스는 실패할 수 있다. 잘못된 공지, 늦은 환불, 방치된 신고는 **"시스템 장애가 아닌 서비스 장애"**다. 이 장은 그 영역을 다룬다.

### 4.1 고객 지원 (CS/VOC) 운영

| 채널 | 1차 응답 목표 (예시) | 해결 목표 | 비고 |
|---|---|---|---|
| 긴급 (결제 오류, 계정 탈취, 개인정보 관련) | 1시간 이내 `[결정 필요]` | 24시간 | 보안·개인정보 건은 CPO 즉시 공유 |
| 일반 문의 | 1영업일 | 3영업일 | |
| 제안·피드백 | 3영업일 | 분기 로드맵 반영 여부 회신 | |

1. 모든 VOC는 **분류 체계**(장애/오류, 사용성, 정책, 결제·환불, 개인정보, 제안)에 따라 태깅하고 월간 집계한다.
2. VOC 중 **장애 의심 건은 15분 내 운영 채널로 전달**한다. CS는 장애의 첫 감지자다.
3. 반복 문의 상위 10건은 월간 운영 리뷰에 보고하고 **제품 개선 또는 도움말 개선**으로 연결한다.
4. 고객 응대 중 개인정보 확인은 **본인 확인 절차**를 거친 후에만 하고, 응대 기록에 불필요한 개인정보를 남기지 않는다.

### 4.2 공지·커뮤니케이션

| 상황 | 공지 시점 | 채널 | 승인 |
|---|---|---|---|
| 계획 점검 (Tier 1) | **최소 3영업일 전** 사전 공지 + 당일 재공지 `[결정 필요]` | 서비스 내 배너, 이메일/푸시, 상태 페이지 | 서비스 오너 |
| P1 장애 | 인지 후 **30분 이내** 1차 공지 (원인 미확정이어도 "확인 중" 공지), 이후 1시간마다 | 상태 페이지, 공식 채널 | 운영총괄 (대행: 운영 관리자) |
| 장애 종료 | 복구 확인 즉시, 영향 범위와 보상 여부 포함 | 동일 | 서비스 오너 |
| 약관·정책 변경 | 법령상 기간 (예: 전자상거래법·약관규제법에 따른 사전 고지 기간) 준수 | 서비스 내 공지, 이메일 | 법무 + 서비스 오너 |

- 장애 공지문 템플릿을 사전에 준비해 두고(현상, 영향, 조치 상황, 다음 업데이트 시각), **법무 검토가 필요한 문구(보상·책임)는 템플릿 단계에서 미리 승인**받는다.

### 4.3 콘텐츠·정책 운영

1. 이용자 생성 콘텐츠(UGC)가 있는 서비스는 **신고 처리 기준과 처리 시한**을 둔다 (예: 불법·유해 콘텐츠 신고는 24시간 내 1차 조치 `[결정 필요]`).
2. 운영 정책(금칙어, 제재 단계, 이의 신청 절차)은 문서화해 CS와 운영팀이 **같은 기준으로 판단**한다.
3. 정책 변경은 변경 이력을 남기고, 이용자에게 영향이 있으면 4.2의 공지 기준을 따른다.

### 4.4 이용자·계정 운영

1. 휴면·탈퇴 처리, 개인정보 파기는 **개인정보 처리방침과 보존 기간 표에 따라 자동화**하고 월간 실행 결과를 기록한다.
2. 관리자 콘솔(어드민)의 이용자 정보 조회·수정은 **사유 입력 + 접속기록 보존** 대상이다.
3. 대량 이용자 데이터 추출(마케팅, 분석)은 **CPO 승인**과 목적·보존 기간 기록을 요구한다.

### 4.5 정산·결제 운영

1. 결제·정산 시스템은 기본적으로 **Tier 1**로 분류한다.
2. 일 마감: 매일 PG사 정산 내역과 자체 결제 기록을 **대사(reconciliation)**하고 불일치는 당일 원인 파악. 월 마감: 재무팀과 공동 마감 체크리스트 운영.
3. 환불·취소 정책과 처리 시한은 CS 기준과 일치시킨다.
4. 정산 로직 변경은 **정상 변경 + 재무팀 승인**을 필수로 한다.

### 4.6 서비스 지표 (KPI) 관리

서비스 오너는 서비스별로 **북극성 지표(North Star Metric) 1개 + 보조 지표 3~5개**를 정해 월간 보고한다. 예시: 활성 이용자(DAU/MAU), 핵심 전환율, 이탈률, 결제 성공률, NPS/CSAT, VOC 건수(1천 이용자당).

- 지표 정의서(계산식, 데이터 출처, 집계 주기, 담당)를 문서화해 **"같은 이름의 지표가 팀마다 다른 숫자"**가 되는 것을 막는다.
- 서비스 지표와 운영 지표(SLO, 장애)는 **같은 월간 보고서**에 담아 상관관계를 본다 (장애가 전환율에 미친 영향 등).

### 4.7 서비스 종료 (Sunset)

1. 서비스 종료는 운영위원회 의결 사항이다. 종료 결정 시 **최소 30일 전 이용자 공지** `[결정 필요]` (법령·약관에 더 긴 기간이 있으면 그에 따름).
2. 종료 체크리스트: 데이터 반환·백업·파기 계획, 개인정보 파기 증적, 외부 연동 해지, 도메인·인증서·클라우드 자원 회수, 카탈로그·CMDB 갱신, 계약·라이선스 정리.
3. 공공 영역의 **전자정부 성과관리 지침**은 운영 성과 측정 결과에 따라 "계속 유지·기능 고도화·통합·폐기"를 판정하도록 하는데, 사내 서비스에도 같은 틀을 적용해 **연 1회 포트폴리오 정비**를 한다.

**[준거]** ITIL 4 service desk·service request·relationship management, ISMS-P 3장(개인정보 처리단계별 요구사항), 전자정부 성과관리 지침(행정안전부 고시)의 운영 성과 측정·정비 체계, 개인정보보호법(파기·처리방침).

## 제5장 SW 유지관리·운영 사업 기준 (대외 계약)

### 5.1 적용 원칙

1. 대외 유지관리·운영 사업은 **제3장의 사내 운영 기준을 기본으로 적용**하고, 고객 계약(SLA, 과업내용서)이 더 엄격하면 계약을 따른다.
2. 계약 전에 **운영 관리자가 SLA 이행 가능성을 검토**해야 하며, 검토 없이 합의한 SLA는 사업관리 담당의 책임이다.
3. 영업·수주 단계에서 "가용성 99.99%" 같은 수치를 쓰려면 **그 수치가 월 4.3분 중단만 허용한다는 의미**를 이해하고, 현재 사내 실적 데이터로 뒷받침되어야 한다.

### 5.2 하자보수와 유지관리의 구분

| 구분 | 하자보수 (Warranty) | 유지관리 (Maintenance) |
|---|---|---|
| 성격 | 계약상 **무상** 의무 | **유상** 계약 |
| 범위 | 검수 완료된 최종산출물의 결함 (요구사항대로 동작하지 않음) | 결함 수정 + 환경 변화 대응 + 성능 개선 + 소규모 기능 개선 등 과업내용서에 정한 범위 |
| 기간 | 소프트웨어 진흥법상 **사업 종료일(시험·검사 후 최종산출물 인도일)부터 1년 이내 범위** | 계약 기간 |
| 제외 | 발주자 제공 물품·지시에 따른 결함(단, 부적절함을 알고도 고지하지 않은 경우 제외), 하자보수기간 경과 후 발생분, 과업에 없던 기능 개선 | 계약 범위 외 신규 개발 (별도 계약) |

- 하자보수 기간 중에도 **"하자인가 변경요청인가"**를 판정하는 기준표를 고객과 사전 합의한다. 이 경계가 불명확하면 무상 추가개발 요구가 반복된다. (2026년 대법원이 공공 SW 과업변경 대가 지급 기준을 제시한 판결이 보도되었으므로 법무와 함께 최신 판례를 확인한다.)
- 하자보수보증금(통상 계약금액의 2%)은 계약서 조건을 따른다.

### 5.3 SLA 설계 표준

대외 SLA는 다음 **5개 필수 지표 + 선택 지표**로 구성한다. 행정안전부가 2026년 공공 SLA 표준(필수지표·점수별 위약금)을 의무화할 계획이므로, 공공 고객은 해당 표준이 확정되면 이에 맞춘다.

| 구분 | 지표 | 정의 | 측정 |
|---|---|---|---|
| 필수 | 서비스 가용률 | (총 서비스 시간 − 비계획 중단 시간) / 총 서비스 시간 | 모니터링 자동 집계, 계획 점검 제외 |
| 필수 | 장애 대응 시간 | 장애 접수 → 대응 착수 | 티켓 시스템 |
| 필수 | 장애 복구 시간 | 장애 접수 → 서비스 정상화 | 티켓 시스템, 등급별 목표 |
| 필수 | 서비스 요청 처리 시간 | 요청 접수 → 완료 | 티켓 시스템, 유형별 목표 |
| 필수 | 보안 조치 이행률 | 취약점·보안 패치 기한 내 이행 비율 | 점검 기록 |
| 선택 | 응답시간(성능), 백업 성공률, 보고서 제출 적시율, 고객 만족도 | 계약별 정의 | — |

SLA 문서 필수 조항: 측정 방식과 데이터 출처, 측정 제외 사유(고객 귀책, 천재지변, 계획 점검, 제3자 서비스 장애), 보고 주기, 미달 시 조치(개선계획 → 위약금/서비스 크레딧), **지체상금과 SLA 위약금의 중복 여부**(공공은 중복 부과 가능 입장이므로 계약 시 명확히), 분쟁 해결 절차.

### 5.4 대가 산정 기준

1. 대외 유지관리·운영 대가는 **KOSA SW사업 대가산정 가이드 (2025년 개정판, 2025.8 공표)**를 기준으로 산정한다.
2. 가이드 구조: **개발비는 기능점수(FP) 방식, 운영·유지관리비는 투입공수 방식**으로 산정 후 합산. 유지관리·운영비 = 고정비 + 변동비 + 직접경비. 비기능 개선 업무는 고정비로 보아 투입공수 방식 운영비로 산정. 응용SW 유지관리비는 요율제 적용.
3. 2025년판 반영 사항: 통합 유지관리 사업에서 **컨소시엄·상용SW 제조사 간 업무 범위와 책임 명확화**, 클라우드 네이티브 환경의 **DevOps형 개발·운영 통합사업 대가 기준** 신설.
4. 구체적 요율·단가는 **KOSA 원문 최신판**을 적용하고, 사내 견적 템플릿에 가이드 버전과 적용 요율을 명기한다.
5. 과업 범위 외 요청은 **변경요청서(CR)**로 접수해 공수·대가를 산정하고 고객 승인 후 수행한다. 구두 요청에 의한 무상 수행은 금지한다.

### 5.5 인력 운영

1. 투입 인력은 과업내용서의 등급·인원과 일치시키고, **교체 시 고객 사전 승인 + 최소 2주 인수인계 기간** `[결정 필요]`.
2. 핵심 인력(PL급)의 백업 담당자를 지정해 **단일 장애점(SPOF)**을 없앤다.
3. 투입 인력은 고객사 보안 규정 교육을 이수하고 증적을 보관한다.
4. 상주 인력의 근태·작업 내역은 **월간 작업 보고서**로 제출한다.

### 5.6 보고 체계

| 보고 | 주기 | 내용 |
|---|---|---|
| 일일 보고 (필요 시) | 매일 | 장애·요청 처리 현황, 당일 작업 |
| 주간 보고 | 주 1회 | 처리 건수·추세, 미결 건, 다음 주 계획, 리스크 |
| **월간 보고** | 월 1회 | SLA 지표 실적 vs 목표, 장애 분석, 변경·배포 내역, 보안 점검, 용량 추세, 개선 제안, 투입 인력 |
| 분기·연간 보고 | 분기/연 | SLA 종합 평가, 시스템 건강도, 차년도 개선·고도화 제안 (전자정부 성과관리 지침의 "유지·고도화·통합·폐기" 판정 틀 활용) |

### 5.7 과업 변경·검수·종료

1. 과업 변경은 **변경요청서 → 영향 분석(공수·일정·SLA) → 고객 승인 → 계약 변경(필요 시)** 순으로 처리하고, 승인 전 착수를 금지한다.
2. 검수는 과업내용서의 산출물 목록과 **대조표(체크리스트)**로 수행하고, 검수 확인서를 받는다.
3. 계약 종료·전환(타 업체 이관) 시 **인계 산출물 목록**(소스·형상, 운영 문서, 계정·권한 목록, 백업, 미결 이슈, 라이선스)을 작성해 고객 확인을 받고, 사내 계정·접근 권한을 **종료일에 회수**한다.

**[준거]** 소프트웨어 진흥법 하자담보책임 조항(1년), KOSA SW사업 대가산정 가이드 2025년 개정판, 행정안전부 공공 SLA 표준 추진(2026), 전자정부 성과관리 지침, ITIL 4 service level management·supplier management, ISO/IEC 20000-1 서비스 수준 관리·공급자 관리 요구사항.

## 제6장 프로젝트·조직 운영 기준

### 6.1 PMO의 역할

PMO(Project Management Office)는 **프로젝트를 대신 수행하는 조직이 아니라, 모든 프로젝트가 같은 규칙으로 보이게 만드는 조직**이다. 비유하면 관제탑이다. 비행기를 직접 조종하지 않지만, 모든 비행기가 같은 언어로 교신하고 충돌하지 않게 한다.

PMO 책임: 프로젝트 등록·분류, 표준 템플릿과 보고 양식, 포트폴리오 우선순위 조정 지원, 리소스 충돌 조정, 리스크 통합 관리, 게이트 심사 운영, 교훈(Lessons Learned) 축적.

### 6.2 프로젝트 분류와 거버넌스 수준

| 등급 | 기준 (예시) `[결정 필요]` | 거버넌스 |
|---|---|---|
| **대형** | 예산 1억 원 이상 또는 6개월 이상 또는 외부 고객 계약 또는 Tier 1 서비스 영향 | 전 게이트 심사, 주간 보고, 운영위원회 보고 |
| **중형** | 예산 2천만~1억 원 또는 1~6개월 | 착수·종료 게이트, 격주 보고 |
| **소형** | 그 외 | 등록 + 종료 보고 |

### 6.3 생애주기와 게이트

PMBOK 7판의 8개 성과영역(이해관계자, 팀, 개발 접근법·생애주기, 기획, 프로젝트 작업, 인도, 측정, 불확실성)을 기준으로, 개발 방식(예측형/애자일/혼합)과 무관하게 아래 **5개 게이트**를 둔다.

| 게이트 | 통과 조건 | 심사자 |
|---|---|---|
| G0 착수 승인 | 목적·기대효과·예산·기간·책임자, 운영 영향 평가(신규 시스템이면 제7장 적용 예고) | 운영위원회 (대형) / 운영총괄 (중·소형) |
| G1 계획 확정 | 범위(WBS 또는 백로그), 일정, 리소스, 리스크 등록부, 품질·보안 요구사항, 이해관계자 소통 계획 | PMO + 스폰서 |
| G2 설계·개발 중간 점검 | 범위 변경 현황, 일정·예산 편차, 리스크 재평가, 운영 준비 착수(런북·모니터링 설계) | PMO |
| G3 오픈 준비 (ORR) | **제7장 운영 준비도 점검 통과** | 운영 관리자 + 보안 담당 + 서비스 오너 |
| G4 종료 | 산출물 인계, 하이퍼케어 종료, 교훈 기록, 예산 정산 | PMO + 스폰서 |

### 6.4 일정·리소스·리스크 관리

1. **일정**: 마일스톤 기준선(baseline)을 G1에서 확정하고, 변경은 변경통제 절차로만 한다. 편차 10% 이상은 보고 `[결정 필요]`.
2. **리소스**: 인력 배정은 PMO가 통합 관리하고, 한 사람의 동시 배정은 **3개 프로젝트 이하** `[결정 필요]`. 운영 업무(온콜 등)를 겸하는 인력은 운영 시간을 먼저 확보한다.
3. **리스크**: 2.4의 공통 척도(가능성×영향)로 관리하고, 15점 이상은 주간 보고에 포함.
4. **범위 변경**: 모든 범위 변경은 영향(일정·예산·품질·운영)을 분석하고 스폰서가 승인한다. 애자일 프로젝트는 백로그 우선순위 변경 권한을 PO에게 두되, **릴리스 목표와 예산 한도는 게이트에서 통제**한다.

### 6.5 회의·보고 표준

| 보고/회의 | 주기 | 양식 핵심 |
|---|---|---|
| 프로젝트 주간 보고 | 주 1회 | 이번 주 완료·다음 주 계획·이슈·리스크·의사결정 요청, **신호등(녹·황·적)** 상태 |
| 포트폴리오 월간 보고 | 월 1회 | 전 프로젝트 상태 요약, 리소스 가동률, 예산 집행률, 적색 프로젝트 조치 |
| 스폰서 의사결정 회의 | 수시 | 1페이지 의사결정 요청서 (배경·선택지·권고·기한) |

보고 원칙: **나쁜 소식은 빨리.** 적색 전환 사유를 숨기지 않은 PM에게 불이익을 주지 않는다는 원칙을 명문화한다.

### 6.6 조직 운영 공통 규칙

1. **의사결정 기록(Decision Log)**: 운영·프로젝트의 주요 결정은 날짜·결정자·선택지·근거를 기록한다. "누가 왜 그렇게 정했는지"가 남지 않으면 같은 논쟁이 반복된다.
2. **온콜 운영**: Tier 1 서비스의 24×7 대응 인력은 **주 단위 로테이션, 1차·2차 담당 지정, 온콜 보상 기준** `[결정 필요]`을 둔다. 연속 온콜은 2주를 넘기지 않는다.
3. **교훈 축적**: 프로젝트 종료·포스트모템의 교훈은 PMO가 분류해 분기마다 기준·템플릿 개정에 반영한다.

**[준거]** PMBOK Guide 7판 (12원칙·8성과영역), ITIL 4 portfolio management·project management·organizational change management·workforce and talent management.

## 제7장 사내 개발 신규 시스템의 운영 전환 기준

### 7.1 원칙

개발이 끝났다고 운영이 시작되는 것이 아니다. **건물이 완공되어도 준공검사·소방점검을 통과해야 입주하는 것**과 같다. 운영 조직은 **운영 준비도 점검(ORR)**을 통과한 시스템만 인수하며, 통과하지 못한 시스템은 개발 조직의 책임으로 남는다.

### 7.2 운영 전환 절차

| 단계 | 시점 | 내용 | 책임 |
|---|---|---|---|
| 1. 운영 영향 평가 | 프로젝트 G0 | 서비스 등급(Tier) 가안, 운영 인력·비용 추정, 기존 서비스 의존성 | 서비스 오너 + 운영 관리자 |
| 2. 운영 요구사항 정의 | G1 | 모니터링·로깅·백업·보안·용량 요구사항을 **개발 요구사항과 동급**으로 백로그에 등록 | 운영 관리자 |
| 3. 운영 준비 착수 | G2 | 런북 초안, 대시보드, 알림, 배포 파이프라인, 백업 구성 | 개발 + 운영 공동 |
| 4. **운영 준비도 점검 (ORR)** | G3 (오픈 2주 전 `[결정 필요]`) | 부록 E 체크리스트 심사. 미통과 항목은 오픈 전 조치 또는 **위험 수용 결정(서비스 오너 서명)** | 운영 관리자(의장), 보안 담당, 서비스 오너 |
| 5. 오픈 및 하이퍼케어 | 오픈 ~ 2~4주 `[결정 필요]` | 개발팀 상주 대응, 일일 공동 점검 회의, 모든 장애 P2 이상으로 취급 | 개발 + 운영 공동 (지휘: 운영 관리자) |
| 6. 운영 인수 확정 | 하이퍼케어 종료 | 종료 조건 충족 확인 → **운영 인수 확인서** 서명, 카탈로그·CMDB 등록, Tier 확정 | 운영총괄 승인 |
| 7. 안정화 리뷰 | 인수 후 3개월 | SLO 실적, 장애 통계, 런북 적정성, 비용 실적 vs 추정 | 월간 운영 리뷰 |

### 7.3 하이퍼케어 종료 조건 (예시)

- 연속 **2주간 P1·P2 장애 없음** `[결정 필요]`
- SLO 측정이 정상 동작하고 2주 실적이 목표를 충족
- 발생한 모든 장애의 런북 반영 완료
- 미결 결함 중 심각도 "높음" 이상 0건
- 운영 담당자가 **개발팀 도움 없이** 복구 테스트와 배포를 1회 이상 수행

### 7.4 인수 거부·연기 기준

다음 중 하나라도 해당하면 운영 조직은 인수를 거부하거나 연기할 수 있다: 롤백 절차 없음, 백업·복구 미검증, 개인정보 처리에 대한 CPO 검토 없음, 운영 계정·권한 분리 없음(개발자 개인 계정으로 운영), 알림에 런북 없음, 외부 의존 서비스 장애 시 동작 미정의.

**[준거]** ITIL 4 service validation and testing·release management·deployment management, ISO/IEC 20000-1 서비스 설계·전환 요구사항, ISMS-P 2.8 정보시스템 도입 및 개발 보안(개발과 운영 환경 분리, 시험 데이터 보안 등).

## 제8장 성과 측정과 지속적 개선

### 8.1 운영 핵심 지표 (전사 대시보드)

| 영역 | 지표 | 주기 | 목표 설정 주체 |
|---|---|---|---|
| 신뢰성 | 서비스별 SLO 달성률, 에러 버짓 잔여율 | 월 | 서비스 오너 |
| 장애 | P1·P2 건수, 평균 복구 시간, 재발 장애 비율, 포스트모템 과제 완료율 | 월 | 운영 관리자 |
| 변경 | 변경 성공률, 긴급 변경 비율(낮을수록 좋음), 변경 금지 위반 건수 | 월 | 운영 관리자 |
| 배포 | DORA 4대 지표 | 월 | 개발 리드 |
| 보안 | 취약점 기한 내 패치율, 권한 검토 완료율, 접속기록 점검 완료율, 보안 교육 이수율 | 월/분기 | CISO/CPO |
| 연속성 | 백업 성공률, 복구 테스트 실시율·RTO 달성 여부 | 분기 | 시스템 운영 |
| 고객 | VOC 1차 응답 준수율, 상위 반복 문의 감소율, CSAT | 월 | CS 리드 |
| 대외 사업 | 고객별 SLA 달성률, 위약금 발생 건, 보고서 적시 제출율, 변경요청 유상 전환율 | 월 | 사업관리 |
| 프로젝트 | 게이트 적시 통과율, 적색 프로젝트 비율, 일정·예산 편차 | 월 | PMO |
| 비용 | 서비스별 클라우드·라이선스 비용, 전월 대비 증감 | 월 | 운영 관리자 |

### 8.2 개선 사이클

ISO/IEC 20000-1과 ISO/IEC 27001은 **Plan–Do–Check–Act** 구조의 지속적 개선을 요구한다. 사내에서는 다음 주기로 운영한다.

- **월간**: 지표 리뷰 → 미달 항목 원인·조치 등록
- **분기**: 운영위원회에서 자원·우선순위 재배분, 기준 예외 검토, 포스트모템 교훈의 기준 반영
- **반기**: **내부 운영 감사** (체크리스트 기반 샘플 점검: 변경 승인 증적, 권한 검토, 백업 테스트, 런북 최신성)
- **연간**: 기준 전면 검토, 서비스 Tier 재분류, BIA 갱신, 외부 인증(ISMS-P/ISO) 추진 여부 결정

### 8.3 개선 과제 관리

모든 개선 과제는 하나의 백로그에서 관리하고 **출처(포스트모템/감사/VOC/지표 미달), 담당, 기한, 상태**를 기록한다. 3개월 이상 지연된 과제는 운영위원회에 보고한다.

## 제9장 예외·위반·개정

### 9.1 예외 승인

1. 이 기준을 적용할 수 없는 사유가 있으면 **예외 신청서**(사유, 기간, 보완 통제, 위험 수용자)를 제출하고 운영총괄(보안 관련은 CISO/CPO 공동)이 승인한다.
2. 예외는 **최대 6개월**이며 연장은 재심사한다 `[결정 필요]`. 예외 목록은 분기 운영위원회에 보고한다.

### 9.2 위반 처리

1. 기준 위반(무승인 변경, 롤백 계획 없는 배포, 권한 미회수, 신고 기한 미준수 등)은 운영 관리자가 기록하고 월간 운영 리뷰에 보고한다.
2. 위반은 **개인 징계보다 재발 방지 설계**를 우선한다. 단, 고의·반복 위반 또는 법정 신고 의무 위반은 인사 규정에 따른다.

### 9.3 개정

1. 정기 개정은 연 1회, 수시 개정은 법령 변경·중대 장애·조직 변경 시.
2. 개정안은 운영위원회 검토 후 승인자가 결재하며, 개정 이력표에 버전·일자·변경 요지·승인자를 기록한다.
3. 개정 시 하위 절차·런북·템플릿의 **영향 목록**을 함께 작성해 갱신한다.

## 부록 A. 서비스 등급 분류 질문지

각 질문에 "예"가 많을수록 상위 등급. 서비스 오너가 작성하고 운영위원회가 확정.

1. 중단 시 1시간 내 매출 손실 또는 계약상 위약금이 발생하는가?
2. 외부 고객·일반 이용자가 직접 사용하는가?
3. 개인정보·결제정보 등 법적 보호 대상 데이터를 처리하는가?
4. 다른 서비스가 이 서비스에 의존하는가 (인증, 결제, 알림 등 공통 서비스)?
5. 중단 시 우회 수단(수동 처리, 대체 시스템)이 없는가?
6. 법령·계약상 가용성 또는 보존 의무가 있는가?
7. 중단이 대외 신뢰·브랜드에 즉시 영향을 주는가 (언론·SNS 확산 가능성)?

판정 가이드(예시): 5개 이상 "예" → Tier 1, 2~4개 → Tier 2, 1개 이하 → Tier 3. 단, 3번이 "예"면 최소 Tier 2.
